Статус: профиль и архитектурный вариант v1 согласованы владельцем 2026-10-31; реализован experimental-пакет, production-приёмка открыта.

При подготовке PR обнаружено: удалённый main уже использует Go 1.27.3. PR сохраняет существующую версию модуля и обновлённые зависимости; согласованная совместимость ядра с Go 1.25 проверена на исходной локальной копии.

## 1. Для кого и зачем

Первый предполагаемый потребитель — auth-go, централизованный сервис входа для собственных web-проектов с backend. Ему нужны passkeys без обязательных email, телефона, пароля и TOTP, несколько ключей на аккаунт, работа на телефоне и ноутбуке, восстановление через recovery-коды и серверные сессии.

Другие потребители — Go-backend и внутренние сервисы, которым нужна регистрация и проверка WebAuthn credentials независимо от HTTP-фреймворка, БД и модели аккаунта. Пользователь библиотеки — backend-разработчик. Конечный пользователь взаимодействует с браузером и аутентификатором: менеджером passkeys, платформенным аутентификатором или аппаратным ключом.

Библиотека должна решать следующие задачи:

- Формировать согласованные параметры регистрации и входа.
- Проверять ответы браузера по явно поддерживаемому профилю WebAuthn.
- Возвращать результат проверки и обновляемые metadata без привязки к БД и cookie.
- Предоставлять небольшой документированный API с явной границей доверия.
- Давать проверяемую основу для повторного использования, независимого review и контролируемой замены внешней реализации.

Самостоятельность означает собственную реализацию серверных правил WebAuthn. Криптографические примитивы должны использовать стандартную библиотеку Go, бинарный CBOR — готовый проверяемый декодер. Копирование большой внешней библиотеки или создание обёртки над ней не считается выполнением этого ТЗ. Внешняя WebAuthn-библиотека допустима как тестовый инструмент сравнения, но не как runtime реализации.

Для auth-go пока используется готовая go-webauthn/webauthn. Выпуск auth-go не зависит от готовности собственной библиотеки. Будущая замена — отдельное согласованное изменение после приёмки и проверки совместимости существующих credentials.

## 2. Границы ответственности

| Область | Библиотека | Потребляющий сервис |
|---|---|---|
| WebAuthn | Options, строгий разбор, проверки и результат | Вызов операций и передача ожидаемого контекста |
| Аккаунт | Непрозрачный user handle и credential | Создание аккаунта, идентификаторы, права |
| Состояние операции | Challenge, назначение, параметры и срок | Защищённое хранение, привязка к браузеру, атомарное расходование |
| Ключи | Проверка public key и metadata | Уникальность credential ID, хранение, отзыв, замена |
| Доступ | Подтверждение конкретной операции | Сессии, OIDC, CSRF, лимиты, TLS, recovery-коды |
| Устройства | Принятие корректного ответа поддержанного профиля | UI и фактическая матрица платформ |

Библиотека не реализует CTAP, Bluetooth, системный QR, Face ID, хранение приватных ключей или синхронизацию passkeys. Этим управляют браузер и провайдер аутентификатора. Синхронизируемый credential нельзя считать уникальным физическим устройством.

Не входят: OIDC provider, PostgreSQL-адаптер, HTTP middleware, Redis, отправка сообщений, управление сессиями и восстановление доступа. Отдельные примеры интеграции нужны, но эти механизмы не становятся зависимостями ядра.

## 3. Предлагаемый профиль первой версии

Это ограниченный профиль WebAuthn, а не обещание реализации всего стандарта. Профиль и публичный API должны быть утверждены до написания кода.

| Параметр | Предложение v1 |
|---|---|
| Роли | Только сервер WebAuthn Relying Party |
| Регистрация | Discoverable credentials: residentKey required; userVerification required |
| Вход | Discoverable и вход для заранее известного пользователя |
| Пользователь | Непрозрачный случайный handle, без обязательных контактных данных; длина по стандарту |
| RP | Один фиксированный RP ID на экземпляр, явный список допустимых origins |
| Контекст | HTTPS; отдельный явно включаемый localhost-профиль разработки |
| Межсайтовое использование | Cross-origin iframe / related origins / AppID не поддерживаются |
| Алгоритм | ES256, EC2/P-256; другие алгоритмы отклоняются как неподдерживаемые |
| Attestation | Запрашивать none, принимать формат none; другие форматы отклонять, не игнорировать |
| Расширения | Не запрашивать; политика ограниченного разбора и обработки описана ниже |
| Key metadata | Credential ID, public key, algorithm, signCount, BE/BS, AAGUID при наличии; transports как необязательная подсказка |

ES256-only и attestation none — осознанные ограничения совместимости. Поддержка Apple/Google/Windows/аппаратных ключей не объявляется заранее: проверяются конкретные сочетания ОС, браузера и провайдера. Если нужная платформа не укладывается в профиль, сначала согласуется расширение ТЗ.

На момент подготовки локальный packages-go использует Go 1.25.6 и единый модуль. Повышение его минимальной версии ради нового пакета требует отдельного согласования. Размещение кода внутри packages-go либо в самостоятельном Go-модуле, имя пакета, версия Go и CBOR-зависимость определяются на архитектурном этапе; положение ТЗ не предрешает упаковку библиотеки.

## 4. Модель угроз и обязательные свойства

Считаем недоверенными все байты ответа браузера, входные идентификаторы и клиентские metadata. Атакующий может отправлять произвольный JSON/CBOR, менять origin/handle, повторять и параллелить операции, использовать свой credential и предъявлять чужие идентификаторы.

Доверенными являются серверная конфигурация, ожидаемое состояние операции и данные credential из доверенного хранилища. Возврат этих данных клиенту и последующее принятие без защиты запрещены в примерах интеграции.

Требования:

1. Нет успеха при неполной проверке; неверные или неподдерживаемые критические данные приводят к ошибке.
2. Нет panic, бесконечной обработки или неограниченного выделения памяти на некорректных данных.
3. Неверный запрос не изменяет переданное credential/state и не возвращает результат, пригодный для выдачи доступа.
4. Нет фоновых сетевых запросов, глобального изменяемого состояния и встроенного логирования пользовательских данных.
5. Параллельные независимые вызовы безопасны. Общая конфигурация после создания неизменяема.
6. Требования относятся к безопасности протокола; они не обещают защиту от полного захвата сервера, устройства, XSS или кражи уже выданной сессии.

## 5. Публичный контракт

До реализации представить типы и сигнатуры четырёх операций: начало регистрации, проверка регистрации, начало входа, проверка входа. Отдельный generic framework, factory и универсальный storage interface не нужны без конкретной необходимости.

Начало операции возвращает браузерные options и серверное состояние. Состояние включает криптографически случайный challenge не менее 32 байт, тип операции, RP/policy, срок, ожидаемый user handle при известном пользователе и идентификатор потока потребителя. Challenge генерируется CSPRNG; ошибка генератора не заменяется слабой случайностью. Срок проверки определяется сервером; browser timeout является подсказкой интерфейсу.

Проверка получает исходные байты ответа, доверенное состояние, текущее время и ожидаемый credential/user context. Часы должны быть контролируемы в тестах. Для discoverable login сервис ищет credential по недоверенному ID, но разрешает доступ только после проверки подписи и соответствия владельца. При known-user login неизвестный/чужой credential запрещён.

Результат регистрации содержит проверенный public credential. Результат входа содержит подтверждённый идентификатор и предлагаемые обновления metadata, включая counter anomaly. Результат сам по себе не является сессией или доказательством атомарного расходования challenge.

Ошибки должны иметь стабильные категории для errors.Is/errors.As: неверный ввод, неподдерживаемая возможность, истёкшее состояние, неверный контекст/challenge, неверный ключ/подпись, невыполненная UV/UP policy, ошибка конфигурации. Точные имена согласуются вместе с API. Детализация не содержит сырых payloads и не требует выдавать причину конечному пользователю.

## 6. Обязательные проверки

### 6.1. Общие

Проверять type операции, challenge после корректного декодирования, точный origin по конфигурации, RP ID hash и допустимый контекст использования. Отсутствующий crossOrigin трактуется согласно спецификации; true отклоняется в v1, связанный topOrigin обрабатывается по выбранному профилю. Не получать допустимый origin из недоверенного Host/forwarded заголовка.

Подпись проверяется над исходными authenticatorData и хешем исходного clientDataJSON; повторная JSON-сериализация запрещена. Поля id/rawId должны согласовываться. Credential type должен быть public-key. Валидация конфигурации отделена от проверки ответа; wildcard origins и небезопасные origins запрещены в production-профиле.

### 6.2. Регистрация

Проверить attestation object, fmt/attStmt, структуру authenticatorData, AT, RP ID hash, UP и UV, длины и credential ID. Для none attStmt должен соответствовать формату. Извлечь COSE public key, проверить kty/alg/crv, координаты и допустимость точки; algorithm должен быть предложен сервером. Приватные компоненты ключа не принимаются.

Дублирование credential в другом аккаунте отклоняется сервисом атомарным ограничением уникальности. excludeCredentials помогает браузеру избежать повторной регистрации, но не заменяет серверное ограничение. Добавление ключа к существующему аккаунту требует свежего подтверждения сервиса; библиотека не может вывести это право из одного ответа регистрации.

### 6.3. Вход

Проверить привязку credential к ожидаемому аккаунту, userHandle, сохранённый ключ, RP ID hash, UP/UV, подпись и все ограничения состояния операции. User handle не должен автоматически создавать пользователя.

Counter policy: если новый или сохранённый signCount ненулевой и новый не увеличился, возвращать явный сигнал аномалии. Нулевые счётчики и синхронизация не должны автоматически объявляться клонированием. Решение отказать или потребовать дополнительное подтверждение принимает сервис по задокументированной политике. BE должен быть согласован с зарегистрированным credential; BS может изменяться, но BS=true при BE=false недопустим. Поддельные metadata обновляются только после успешной проверки.

### 6.4. Строгий разбор

Перед реализацией закрепить численные пределы: общий ответ, clientDataJSON, authenticatorData, credential ID, CBOR depth/items и количество credentials в options. Исходное предложение: общий ответ 64 KiB, clientDataJSON 8 KiB, CBOR depth 16; уточнить нормативные границы отдельных полей по стандарту. Проверять длины до slicing/allocations, отклонять усечение, неоднозначные дубли ключей и невалидные типы.

Неизвестные необязательные JSON-поля допустимы только по документированной политике совместимости и не влияют на разрешение доступа. Неизвестные значения алгоритмов/attestation не игнорируются. При ED структура extension data разбирается с лимитами и проверкой границ; необязательные неизвестные extension outputs не дают прав и не используются как доказательство. Обработка trailing bytes, reserved bits и неизвестных полей должна соответствовать явно указанным правилам версии стандарта, а не произвольному правилу «запретить всё неизвестное».

## 7. Одноразовость и интеграция с хранилищем

Сама проверяющая функция не может предотвратить повторный вызов с теми же аргументами. Пример интеграции обязан демонстрировать завершение операции одной транзакцией: проверить актуальность pending state, credential и account generation, атомарно отметить challenge использованным, сохранить результат/metadata и создать разрешённый сервисом результат входа. При конкуренции успешен только один commit.

При отзыве credential или восстановлении аккаунта между криптографической проверкой и commit сервис повторно проверяет актуальность credential/account generation. Ошибка БД не превращается в успешный вход. Библиотека не удерживает глобальный mutex и не считает память процесса общим хранилищем реплик.

## 9. Приёмка и доказательства

Для каждого ID матрицы указать тест или запись ручной проверки, версию библиотеки, команду и результат. Сценарии разных повреждённых полей параметризуются, а не закрываются одним happy-path тестом.

Обязательны unit tests, go test -race, fuzz targets для JSON/CBOR/authenticator data и публичных finish-операций, фиксированные независимые векторы, тесты границ размеров и времени. Fuzzing ограничивается согласованным бюджетом и сохраняет найденные regressions. Сравнение с go-webauthn помогает находить расхождения, но эталоном остаётся стандарт: совпадение двух реализаций не доказывает правильность.

Для браузерных automated tests допускается virtual authenticator. Он не доказывает работу реальных Apple/Google/Windows providers, синхронизации и QR; для них нужна ручная матрица с точными версиями ОС/браузера/провайдера. Таблица соответствия должна связать шаги нормативных алгоритмов регистрации/входа с кодом и тестами, отметить сознательно исключённые возможности.

До production требуется независимое security review с закрытием подтверждённых дефектов. До выполнения этой приёмки библиотека обозначается experimental. Сертификация FIDO/WebAuthn не заявляется на основании локальных тестов.

## 10. Поставляемые материалы и этапы

1. Согласованные профиль, размещение модуля, Go-версия, зависимости и публичный API с примерами входных/выходных типов и ошибок.
2. Реализация конфигурации, options/state, строгого разбора и проверок регистрации вместе с соответствующими тестами.
3. Реализация входа, metadata/counter policy и параллельной безопасности вместе с тестами.
4. Минимальный браузерный пример и транзакционный пример интеграции, проверяющие сценарии И; без подключения к production auth-go.
5. README: установка, поддерживаемый профиль, ограничения, границы ответственности, рабочие примеры, хранение state, обработка ошибок и политика обновлений.
6. Матрица приёмки, fuzz/regression corpus, независимое review, подтверждённый список платформ.
7. Отдельное предложение миграции auth-go: формат сохранённых credentials, пробная проверка, включение, откат. Автоматическая подмена текущей библиотеки этим ТЗ не разрешена.

Каждый этап проверяется до следующего; tests и документация выполняются вместе с функцией. Изменения версии Go, публичного API, расширение профиля и выделение нового репозитория требуют согласования владельца. Коммиты, push и публикация выполняются только по отдельному разрешению.

## 11. Бэклог после первой версии

- Дополнительные алгоритмы, форматы attestation и доверенные metadata — по конкретной потребности устройств.
- Расширения WebAuthn, conditional UI, cross-origin/related origins — с отдельной моделью угроз.
- Поддержка legacy U2F/AppID, enterprise attestation и attestation trust chains.
- Формальная сертификация и расширенная аппаратная матрица.

Способы восстановления аккаунта остаются задачей auth-go, а не протокольной библиотеки. Ни TOTP, ни recovery-коды не добавляются в ядро WebAuthn ради восстановления.
